## 🔴 F1 (HEADLINE) — docker_exec in-container `timeout` breaks on busybox/Alpine images
`dockerHelpers.ts:269-276 buildInContainerTimeout` probes `command -v timeout` (present/absent) but then unconditionally emits **GNU long-option syntax** `timeout --signal=TERM --kill-after=5 <secs> sh -c …`. BusyBox `timeout` only accepts `-s SIG -k KILL_SECS` → rejects `--signal=` → **exit 1, the inner command never executes**. This is the SAME bug class as prior-pass #4 (G3), which fixed "timeout absent" (distroless 127) but not "timeout is busybox" (Alpine exit 1). Affects every Alpine/busybox-based container (gluetun, and likely tailscale, watchtower, scrutiny, the linuxserver s6 images use bash so vary). **Fix:** emit portable short options `timeout -s TERM -k 5 <secs> <shell> -c …` — accepted by BOTH GNU coreutils and busybox v1.37 (`timeout [-s SIG] [-k KILL_SECS] SECS PROG`). One-line change. Add an integration fixture for a busybox image.

## 🟡 F2 — docker_exec on shell-less (distroless) images: honest but dead-end
portainer-ce is distroless: no `sh`. `docker exec … sh -c` → `exec: "sh": executable file not found` exit 127. Inherent (can't exec without a shell). **Fix (minor):** detect the `"sh": executable file not found` / 127 signature and return a typed "container has no shell (distroless); docker_exec unsupported" message; document the limitation on the tool. Not blocking.

## 🟡 F3 — repeated auto-latest revert fails on reverse-delta backups + misleading guidance
After revert #1 (auto-latest), revert #2 (auto-latest) on the same file threw `Cannot apply delta backup: the current file has changed since this backup was created (base 0678cf0f…, current 4fdbc441…)`. Root cause: `revert_file` does **not** snapshot the pre-revert state, so the "newest backup" stays the reverse-delta keyed to the `BETA-edited` base that revert #1 just overwrote → its base no longer matches. Two sub-issues: (1) the error guidance *"Try reverting a more recent backup first"* is **misleading** — there is no more-recent backup; the real fix is to revert the self-contained full backup or re-anchor. (2) The F6 auto-latest convenience silently picks an un-appliable delta the moment the file has been reverted once. **Consider:** (a) have `revert_file` write a fresh backup of the pre-revert content (so the chain stays appliable + revert is itself revertible); and/or (b) when the newest delta's base ≠ current, auto-fall-back to the newest *self-contained/appliable* backup; and/or (c) fix the guidance text. Note ADR-014 re-anchor exists — verify it covers the revert path.

## 🔴 F5 — docker_logs relative `since` is broken for ALL relative values (validator vs forwarder mismatch)
`dockerHelpers.ts:305-312 buildDockerLogsCommand` forwards the validated `since` straight to `docker logs --since '<value>'` with **no translation** (comment literally says *"already validated by the handler (tail_log grammar)"*). But journalctl understands `"30 min ago"` while `docker logs --since` only takes Go durations (`30m`,`2h`) / RFC3339:
  - `since:"2h"` → **server validator rejects** (`Use … "<n> min|hour|day ago"`).
  - `since:"30 min ago"` / `"2 hour ago"` → server accepts, **docker rejects** (`failed to parse value as time or duration`).
  → **No relative `since` works at all**; the schema's own `"30 min ago"` example is non-functional. Same value works fine on `tail_log` (it translates for journalctl). **Fix:** in `buildDockerLogsCommand`, translate the tail_log grammar to a docker-acceptable value — map `<n> min|hour|day ago` → Go duration (`<n>m`/`<n>h`/`<n*24>h`; docker has no `d` unit) or, cleaner, to an absolute RFC3339 (`now − delta`). ISO passthrough is fine (docker accepts RFC3339). Add a fixture asserting `--since` gets a docker-parseable value.

## 🔴 F8 (HEADLINE) — guest_backup_restore searches the wrong storage → backup/restore round-trip is broken
`backupTools.ts:242` restore handler: `const storage = cfg.backup.nodeBackupStorage` (default `"local"`, config.ts:75/404) and lists `/storage/local/content` for the archive — **ignoring the storage prefix in the provided `archive` volid** (`media-backup:backup/…`). Proven live: the *correct* volid for an archive verified present on `media-backup` still errors `not found … on local`. Since `local` lacks the `backup` content-type (the whole reason #9/G1 added `storage:` to guest_backup), **no archive guest_backup can create is ever findable by restore.** The G1 fix added `storage` to the WRITE side but not the READ side — same bug class as prior-pass #9, now on restore. **Fix:** derive storage from the volid — `assertVolid`/parse already exists (`backups.ts:127-134`), use `parseVolid(input.archive).storage` instead of the config default; OR add a `storage` param mirroring guest_backup. Add a restore fixture with a non-`local` volid.

## 🟡 F9 — vzdump archive lifecycle is unmanageable through MCP (discovery + delete + TZ skew)
Three compounding gaps around mcp- archives: **(a) volid not discoverable** — `guest_backup` returns the task UPID + the note (`mcp-20260625-002133`, **UTC**) but not the archive volid, and vzdump names the file in **node-local time** (`…-2026_06_24-19_21_33.tar.zst`) → you cannot reconstruct the volid from the tool's own output (TZ skew). **(b) no list tool** — nothing surfaces existing archives; at companion tier there's no host exec to `ls` the storage (I only found it because CT101 happens to bind-mount the backup dir). **(c) no delete tool** — `guest_backup` creates, retention evicts only on the *next* backup; there's no explicit archive delete, and `pct_exec` into the unprivileged 101 gets `Permission denied` (files are host-root/`nobody`). Net: after a backup you can neither drive a restore (need the volid) nor clean up. **Fix:** `guest_backup` should return the resulting `volid` (post-task, from the storage content list); add a small `guest_backup_list`/archive-discovery read tool (companion, API-native — `/storage/<s>/content?content=backup` already used by retention); consider an mcp-only archive delete. Cross-cutting **timezone theme:** also the snapshot `description` ("2026-06-24 19:20:21" local) vs `name` ("mcp-20260625-002019" UTC) — pick one TZ (UTC) for all server-generated names/notes.
